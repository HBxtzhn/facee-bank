- **单线程设计原因**：
  - Redis 核心瓶颈是内存和网络，而非 CPU，单线程足够快。
  - 单线程避免了多线程锁竞争和上下文切换的开销。
  - 单线程天然保证命令执行的原子性，无需复杂的并发控制。
  - 实现简单，易于维护和调试。
- **6.0 引入多线程的原因**：
  - 随着网络硬件性能提升，网络 I/O 成为瓶颈（尤其是大 key 场景）。
  - 多线程用于处理网络读写和协议解析，命令执行仍为单线程。
  - 通过 `io-threads` 和 `io-threads-do-reads` 配置开启，默认关闭。

## 扩展知识

- **单线程的局限**：单核 CPU 无法利用多核优势；大 key 操作（如 `DEL` 大对象、`LRANGE` 大列表）会阻塞整个服务。解决方案：`UNLINK`（异步删除）、`LAZYFREE`、`SCAN` 替代 `KEYS`。
- **Redis 6.0 多线程架构**：主线程负责命令执行，I/O 线程负责读写 socket 和解析 RESP 协议。流程：I/O 线程读取客户端请求 → 主线程执行命令 → I/O 线程写回响应。
- **线程安全**：I/O 线程只处理网络 I/O，不执行命令，因此不需要加锁。主线程和 I/O 线程之间通过事件通知协调。

## 对比表格

| 维度 | Redis < 6.0（纯单线程） | Redis >= 6.0（I/O 多线程） |
|------|------------------------|--------------------------|
| 命令执行 | 单线程 | 单线程（不变） |
| 网络 I/O | 单线程 | 多线程并行处理 |
| 协议解析 | 单线程 | 多线程并行处理 |
| 原子性保证 | 天然保证 | 仍然保证（命令执行串行） |
| 性能提升 | 基准 | 吞吐量提升约 1 倍 |
| 默认开启 | - | 默认关闭，需手动配置 |
