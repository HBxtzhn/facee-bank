GC调优是系统性工作，不是上来就改参数。一般按以下步骤进行：

## 第一步：明确目标，监控现状

先搞清楚现状和目标，不要盲目调优：

1. 确定业务目标：是低延迟优先还是吞吐量优先

2. 开启GC日志：`-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:gc.log`

3. 用工具分析：GCViewer、GCEasy、jstat等

4. 统计关键指标：Young GC频率/耗时、Full GC次数、老年代增长率、最大停顿

## 第二步：选择合适的垃圾收集器

根据业务场景选收集器：

- **吞吐量优先**：Parallel Scavenge + Parallel Old（Java8默认）

- **低延迟优先（中小堆）**：ParNew + CMS

- **低延迟优先（中大堆）**：G1（Java9+默认）

- **超低延迟（大堆）**：ZGC（Java15+）

## 第三步：调整堆大小和分代比例

**堆大小设置：**

- `-Xms`和`-Xmx`设成一样，避免堆动态扩容的开销

- 一般设为物理内存的50%~70%，留够系统和其他进程用

- 不是越大越好，太大了GC一次时间也长

**分代比例：**

- 新生代默认是堆的1/3，可以根据对象生命周期调整

- 对象死得快、朝生夕灭多 → 加大新生代

- 长生命周期对象多 → 加大老年代

- `-XX:NewRatio` 新生代和老年代比例，默认2（老年代:新生代=2:1）

- `-XX:SurvivorRatio` Eden和Survivor比例，默认8

## 第四步：针对性优化常见问题

**频繁Young GC：**

- 现象：Young GC很频繁，每次回收量也不大

- 解决：加大新生代空间（-Xmn调大）

**频繁Full GC、老年代增长快：**

- 现象：老年代占用持续上涨，Full GC频繁

- 先排查是不是内存泄漏，这是最常见原因

- 不是泄漏的话：调大老年代、提高晋升年龄阈值、让对象尽量留在新生代

**CMS的Concurrent Mode Failure：**

- 调小`CMSInitiatingOccupancyFraction`，让CMS早点开始

- 加大老年代空间

- 开启Full GC压缩

**G1停顿时间不达标：**

- 调整`MaxGCPauseMillis`目标值，不要设得太激进

- 加大堆内存

- 检查是不是有大对象、巨型对象太多

## 第五步：验证效果，持续迭代

- 改完参数压测验证，对比调优前后的GC指标和业务指标

- GC调优不是一次到位的，需要多次迭代微调

- 上线后持续监控，业务变化后可能需要重新调优

## 调优原则

1. **优先排查代码问题**：很多GC问题本质是代码写得不好（内存泄漏、大对象），先优化代码再调参数

2. **不要过度调优**：满足业务需求就行，GC有少量开销是正常的

3. **默认值通常不错**：JVM默认参数经过大量验证，没明显问题不要乱改

4. **一次只改一个参数**：改多个不知道哪个起作用，出问题也不好回滚
