1. **核心概念**：Redis 分布式锁在实际使用中面临多种问题，包括锁过期、锁误删、主从切换、RedLock 争议等，需要综合方案解决。
2. **关键细节拆解**：
   - **锁过期问题**：业务未完成锁已过期 → Watch Dog 续期
   - **锁误删问题**：客户端 A 删除了客户端 B 的锁 → value 使用唯一标识 + Lua 脚本原子校验删除
   - **主从切换丢锁**：客户端 A 在主节点加锁成功，主节点挂掉，锁未同步到从节点，从节点提升为主后，客户端 B 可以获取到锁 → RedLock 或接受 AP 模型的弱一致性
   - **不可重入问题**：同一线程多次获取同一把锁导致死锁 → 使用可重入锁（Redisson RLock）
   - **公平性问题**：先请求的客户端不一定先获取锁 → 使用公平锁（Redisson FairLock）
   - **超时与重试**：获取锁失败后的重试策略 → 指数退避或固定间隔重试

## 扩展知识

- **主从切换丢锁详解**：客户端 A 在 master 上执行 `SET lock_key value NX PX 30000`，命令返回成功但锁尚未同步到 slave。此时 master 宕机，slave 被提升为新 master。客户端 B 向新 master 发送相同的加锁请求，由于新 master 上没有 lock_key，B 成功获取锁。此时 A 和 B 同时持有锁。
- **RedLock 对此的解决**：通过多数派机制，加锁需要在 N/2+1 个独立节点上成功，单个节点的主从切换不影响整体锁的安全性（但 RedLock 本身也有争议）。
- **锁的可靠性分级**：
  - **效率型**：防止重复操作，允许偶尔失效 → 单节点 Redis 锁
  - **安全型**：严格互斥，不允许并发 → ZooKeeper/etcd 锁
- **Redis Cluster 下的锁**：在集群模式下，锁 key 会被分配到特定 slot，该 slot 的主节点故障时同样存在主从切换丢锁问题。

## 对比表格

| 问题 | 原因 | 解决方案 | 方案局限性 |
|------|------|---------|-----------|
| 锁过期 | 业务耗时超预期 | Watch Dog 续期 | GC 停顿可能导致续期失败 |
| 锁误删 | 未校验锁归属 | value 唯一标识 + Lua 脚本 | 实现复杂度增加 |
| 主从切换丢锁 | 锁未同步到从节点 | RedLock / 接受弱一致 | RedLock 有争议 |
| 不可重入 | 同一线程重复加锁 | 可重入锁（Hash 结构） | 需要维护重入计数 |
| 不公平 | 无排队机制 | 公平锁（ZSet 排队） | 性能略低 |
| 获取超时 | 竞争激烈 | 重试 + 超时机制 | 增加系统复杂度 |
