1. **核心概念**：RedLock（Redis Distributed Lock）是 Redis 作者 antirez 提出的一种基于多个独立 Redis 实例的分布式锁算法，旨在解决单点 Redis 故障导致锁失效的问题。
2. **关键细节拆解**：
   - **架构**：使用 N 个（通常 5 个）完全独立的 Redis 主节点，无主从复制。
   - **加锁流程**：
     1. 获取当前时间戳 `start_time`
     2. 依次向 N 个节点发送 `SET key unique_value NX PX ttl` 请求
     3. 如果在超过 N/2+1 个节点上成功获取锁，且总耗时小于 ttl，则加锁成功
     4. 实际锁的有效时间 = ttl - 加锁总耗时 - 时钟偏移
     5. 如果加锁失败，向所有节点发送解锁请求
   - **解锁**：向所有 N 个节点发送删除锁的请求
   - **核心思想**：通过多数派（quorum）机制，即使个别节点故障，锁仍然有效

## 扩展知识

- **争议**：Martin Kleppmann 与 antirez 关于 RedLock 安全性的著名争论。Martin 指出 RedLock 依赖系统时钟，而时钟跳跃（NTP 同步、GC 停顿、网络延迟）可能导致锁失效。antirez 承认在某些极端场景下 RedLock 不够安全。
- **时钟依赖问题**：RedLock 的 TTL 依赖各节点的时钟，如果某个节点发生时钟跳跃（向前），可能导致锁提前过期。
- **替代方案**：ZooKeeper（强一致性，CP 模型）、etcd（基于 Raft）、Consul 等更适合需要强一致性的分布式锁场景。
- **Redisson 的 RedLock 实现**：`RedissonRedLock` 封装了多个 `RLock`，向所有节点加锁，超过半数成功则返回成功。
- **实际使用建议**：如果业务可以容忍锁偶尔失效（如效率型锁），可以使用单节点 Redis + Watch Dog；如果需要强一致性（如资金操作），建议使用 ZooKeeper 或 etcd。

## 对比表格

| 特性 | 单节点 Redis 锁 | RedLock | ZooKeeper 锁 | etcd 锁 |

| 一致性模型 | AP | AP（弱） | CP | CP |
| 时钟依赖 | 低 | 高 | 低（基于会话） | 低（基于 Raft） |
| 性能 | 高 | 中 | 中 | 中 |
| 强一致性 | ❌ | 争议 | ✅ | ✅ |
| 实现复杂度 | 低 | 高 | 中 | 中 |
