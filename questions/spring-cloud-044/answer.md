1. **定义**：服务网格（Service Mesh）是一种基础设施层，用于处理微服务之间的通信。它把服务治理能力（负载均衡、熔断限流、链路追踪、安全认证等）从业务代码中抽离出来，以 Sidecar 代理的形式部署在每个服务旁边。

2. **核心组件**：
   - **数据平面（Data Plane）**：Sidecar 代理（如 Envoy），跟服务部署在一起，拦截所有进出服务的网络流量，负责实际的服务治理（路由、负载均衡、熔断等）。
   - **控制平面（Control Plane）**：控制面（如 Istio 的 istiod），负责管理和配置所有的 Sidecar，下发路由规则、安全策略等。

3. **核心优势**：
   - **业务解耦**：服务治理能力下沉到基础设施层，业务代码不需要关心熔断、限流、链路追踪等逻辑。
   - **多语言支持**：Sidecar 是独立的进程，拦截网络流量，不依赖特定语言。Java/Go/Python/Node 服务都能用同一套服务治理方案。
   - **统一治理**：所有服务的 Sidecar 由控制面统一管理，策略变更全局生效。

4. **代表产品**：Istio（最流行，Google 主导）、Linkerd（轻量级）、Consul Connect。

5. **缺点**：引入 Sidecar 增加了资源消耗（每个服务多一个进程）和网络延迟（请求多一跳）；运维复杂度增加（需要管理 Sidecar 的部署、升级、监控）；学习曲线陡峭。

## 扩展知识

- **Sidecar 模式**：Sidecar 是一个跟主应用容器一起部署的代理容器（K8s Pod 里有两个容器）。所有进出主应用的流量都经过 Sidecar。Sidecar 负责服务发现、负载均衡、熔断限流、加密认证、链路追踪等。
- **Istio 的流量管理**：通过 VirtualService（路由规则）和 DestinationRule（目标规则，定义负载均衡、连接池、熔断策略）控制流量。支持流量镜像、故障注入、灰度发布等高级功能。
- **服务网格 vs Spring Cloud**：Spring Cloud 的服务治理能力在应用层（SDK 形式），跟业务代码耦合。服务网格的能力在基础设施层（Sidecar 形式），跟业务代码解耦。Spring Cloud 只支持 Java，服务网格支持多语言。

## 概念对比

| 维度 | Spring Cloud | 服务网格（Istio） |
|------|-------------|------------------|
| 治理位置 | 应用层（SDK） | 基础设施层（Sidecar） |
| 语言支持 | 主要 Java | 多语言 |
| 侵入性 | 需要引入 SDK | 业务代码零侵入 |
| 资源消耗 | 低 | 较高（每个服务多一个Sidecar） |
| 运维复杂度 | 中 | 高 |
| 适用场景 | Java 为主的微服务 | 多语言混合的微服务 |
