- **历史背景**：Redis 早期版本（2.x 之前）提供过虚拟内存功能，允许将部分不常用的数据交换到磁盘，以突破物理内存限制。**Redis 2.6 之后已移除该功能**。
- **设计思路**：将热数据保留在内存，冷数据序列化到 swap 文件。访问冷数据时从磁盘加载回内存，可能将其他热数据交换出去。
- **被移除的原因**：① 性能不可预测（swap 操作导致延迟尖刺）；② 实现复杂，bug 多；③ SSD 普及后效果不如预期；④ 社区推荐使用更可靠的方案替代。
- **现代替代方案**：Redis 4.0+ 的内存淘汰策略（`maxmemory-policy`）、Redis on Flash（Tair 实现）、分层存储。

## 扩展知识

**早期 VM 机制的工作方式**：
- 配置参数：`vm-enabled`、`vm-swap-file`、`vm-max-memory`、`vm-max-threads`
- 当内存使用超过 `vm-max-memory` 时，Redis 将不常用的 key 的 value 序列化到 swap 文件
- key 本身始终保留在内存中（用于快速查找），只有 value 被交换
- 交换粒度是整个 value，不能部分交换

**为什么 VM 方案失败**：
1. **延迟不可控**：磁盘 IO 延迟是内存的 10^5 倍，swap in/out 导致请求延迟剧烈波动
2. **内存中仍需存储 key**：key 的内存占用无法节省，对于大 value 场景有效，但小 key 场景收益低
3. **并发问题**：多线程 swap 操作引入锁竞争
4. **更好的替代方案出现**：内存淘汰策略 + 外部缓存（如本地磁盘缓存）更可控

**现代 Redis 的内存扩展方案**：
- `maxmemory-policy`：8 种淘汰策略（noeviction/allkeys-lru/volatile-lru/allkeys-lfu 等）
- 阿里云 Tair（Redis 增强版）支持 Redis on Flash，将冷数据持久化到 SSD
- 客户端层面做冷热分离：热数据用 Redis，冷数据用 RocksDB/HBase 等

## 对比表格

| 特性 | Redis VM（已移除） | 内存淘汰策略 | Redis on Flash（Tair） |
|------|-------------------|-------------|----------------------|
| 状态 | 已废弃（2.6+） | 当前主流方案 | 商业方案 |
| 数据位置 | 内存 + swap 文件 | 仅内存 | 内存 + SSD |
| 延迟稳定性 | 差（swap IO 不可控） | 好（纯内存） | 较好（SSD 加速） |
| 数据容量 | 受 swap 文件大小限制 | 受物理内存限制 | 远超物理内存 |
| 实现复杂度 | 高 | 低 | 高 |
| 适用场景 | 已不适用 | 通用场景 | 大数据量 + 成本敏感 |
