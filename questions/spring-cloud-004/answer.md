1. **整体架构**：Nacos Config 采用 C/S 架构，客户端通过 gRPC 长连接与服务端通信。配置存储在后端数据库（MySQL）中，服务端负责配置的增删改查和变更推送。

2. **配置拉取**：服务启动时，客户端通过 gRPC 向 Nacos Server 发起配置查询请求，拿到配置后缓存在本地内存和本地文件快照（/nacos/config/ 目录下）。

3. **配置变更推送（长轮询）**：Nacos 2.x 用 gRPC 长连接推送，服务端检测到配置变更后主动通知所有监听了该配置的客户端。1.x 版本用的是 HTTP 长轮询，客户端发起请求后服务端 hold 住请求，有变更才返回，超时（默认30s）也返回。

4. **本地快照容灾**：客户端每次拉到配置都会写一份本地快照文件，如果 Nacos Server 全部挂了，客户端可以从本地快照读取配置启动，保证服务可用性。

5. **配置分组与 DataId**：通过 Namespace（命名空间）+ Group（分组）+ DataId（配置ID）三级定位唯一一份配置。默认 Namespace 是 public，默认 Group 是 DEFAULT_GROUP。

6. **配置加密**：支持 AES、RSA 等加密方式，敏感配置在 Nacos 里加密存储，客户端拉取后自动解密。

## 扩展知识

- **长轮询 vs gRPC 推送**：Nacos 1.x 的长轮询机制是客户端发起 HTTP 请求，服务端 hold 住 30 秒，期间如果有配置变更就立即返回，否则 30 秒后返回 304 无变更。客户端收到响应后立即再发起下一次请求。这种方式有最多30秒的延迟。Nacos 2.x 改为 gRPC 长连接，服务端可以实时推送，延迟降到毫秒级。
- **配置一致性保证**：Nacos 集群模式下，配置写入遵循 Distro 协议（AP）或 Raft 协议（CP）。默认是 AP 模式，配置写入主节点后异步复制到从节点，保证最终一致性。
- **灰度发布**：Nacos 支持配置灰度发布，可以指定部分 IP 的机器先收到新配置，验证没问题再全量推送。
- **配置监听源码**：NacosConfigService.addListener() → 注册监听器 → ClientWorker 里的 ConfigRpcTransportClient 负责跟服务端通信。
