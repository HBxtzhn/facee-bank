1. **核心思想**：把一个大的单体应用拆成多个小的、独立部署的服务，每个服务围绕特定的业务能力构建，服务之间通过轻量级机制（HTTP/RPC/MQ）通信。

2. **独立部署**：每个微服务有自己的进程，可以独立部署、独立升级，一个服务的变更不需要重新部署其他服务。

3. **去中心化**：技术栈可以去中心化（不同服务可以用不同的数据库、甚至不同的语言），治理可以去中心化（每个服务自己管理自己的数据和逻辑）。

4. **业务边界清晰**：微服务的拆分应该按照业务领域来划分，参考 DDD 的限界上下文。一个服务对应一个业务域，比如订单服务、用户服务、支付服务。

5. **基础设施支撑**：微服务需要一整套基础设施来支撑——注册发现、配置中心、网关、熔断限流、链路追踪、CI/CD。没有这些基础设施，微服务就是灾难。

6. **不是银弹**：微服务不是万能的，小项目用微服务是过度设计。团队规模小、业务简单的项目，单体应用更合适。

## 扩展知识

- **康威定律**：设计系统的组织，其产生的设计等同于组织之内、之间的沟通结构。微服务的拆分应该跟团队结构对齐，一个团队负责几个服务。
- **微服务的数据管理**：每个服务拥有自己的数据库（Database per Service），不能直接访问其他服务的数据库，只能通过 API 交互。这带来了分布式事务的挑战。
- **生产实践**：微服务落地最大的挑战不是技术，而是组织。需要 DevOps 文化、CI/CD 流水线、容器化部署、监控告警体系等配套。
