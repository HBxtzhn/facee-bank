GC调优不是追求GC次数越少越好，而是围绕业务目标平衡多个指标。核心目标按优先级排序：

## 1. 可用性：避免Full GC和长时间STW

- **最高优先级目标**：Full GC会导致长时间卡顿，严重影响业务可用性

- 特别是CMS的concurrent mode failure、G1的Full GC，一次停顿几秒到几十秒

- 调优首先要消除频繁Full GC，这是底线

## 2. 延迟：控制最大停顿时间（Latency）

- 对于交互型业务（Web应用、接口服务），响应时间很重要

- GC停顿直接影响接口RT（响应时间），尤其是P99延迟

- 目标：把最大停顿控制在业务可接受范围内（比如100ms以内）

- 对应收集器：CMS、G1、ZGC这些低延迟收集器

## 3. 吞吐量：提高业务代码占比（Throughput）

- 吞吐量 = 用户代码执行时间 / 总时间

- 对于后台计算型任务（数据分析、批处理），吞吐量更重要

- GC占用CPU越少，跑业务的时间就越多

- 目标：GC开销控制在5%~10%以内

- 对应收集器：Parallel Scavenge + Parallel Old

## 4. 内存占用：合理使用堆空间

- 在满足前三个目标的前提下，尽量节省内存

- 堆不是越大越好，太大了单次GC时间也会长

- 目标：用最小的堆满足业务需求，节省机器成本

## 调优的核心矛盾

延迟和吞吐量是一对矛盾体：

- 低延迟收集器（CMS、ZGC）有并发开销，吞吐量相对低

- 高吞吐量收集器（Parallel GC）STW长，延迟高

- G1是中间路线，兼顾两者

调优前必须明确业务更看重什么，不能两头都要。
