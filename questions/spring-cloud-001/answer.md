1. **业务场景**：当一个大操作跨了多个微服务或者多个数据库，要么全部成功，要么全部回滚，这时候就需要分布式事务。典型的比如电商下单——订单服务写订单、库存服务扣库存、积分服务加积分，三个服务三个库，任何一个失败都得回滚。

2. **2PC（两阶段提交）**：最经典的方案，有一个事务协调者（TC），先问所有参与者能不能提交（Prepare阶段），大家都说OK再统一Commit。缺点是同步阻塞、性能差，数据库资源长时间被锁定。

3. **TCC（Try-Confirm-Cancel）**：业务层面的两阶段，Try阶段预留资源，Confirm确认提交，Cancel取消释放。好处是不依赖数据库层面的锁，性能好；缺点是侵入性强，每个业务接口都要写三个方法。

4. **本地消息表 + MQ 最终一致性**：事务发起方在本地事务里同时写业务数据和消息表，然后通过定时任务或MQ把消息发出去，下游消费成功就提交。这种方案实现简单，适合对一致性要求不是特别实时的场景。

5. **Seata**：阿里开源的分布式事务框架，支持 AT、TCC、Saga、XA 四种模式，跟 Spring Cloud 集成非常方便。

6. **最大努力通知**：比如支付完成后回调通知商户，通知失败会按策略重试多次，属于最终一致性方案。

## 扩展知识

- **AT 模式原理**：Seata AT 基于一阶段本地提交 + 二阶段异步补偿。一阶段拿到全局锁后本地事务直接提交，同时记录 before/after image 到 undo_log 表；二阶段如果需要回滚，就根据 undo_log 生成反向 SQL 执行补偿。
- **生产踩坑**：AT 模式要求业务库和 undo_log 在同一个数据源，跨库不行；全局锁在高并发下会成为性能瓶颈，可以考虑用 TCC 替代。
- **选型建议**：强一致性用 XA 或 Seata AT；高性能场景用 TCC；最终一致性用本地消息表或 RocketMQ 事务消息。

## 概念对比

| 方案 | 一致性 | 性能 | 侵入性 | 适用场景 |
|------|--------|------|--------|----------|
| 2PC/XA | 强一致 | 低 | 低 | 传统银行系统 |
| TCC | 最终一致 | 高 | 高 | 订单、资金类 |
| Seata AT | 最终一致 | 中 | 低 | 大部分CRUD业务 |
| 本地消息表 | 最终一致 | 高 | 中 | 异步解耦场景 |
| Saga | 最终一致 | 高 | 中 | 长事务、跨组织 |
