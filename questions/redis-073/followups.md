## 追问 1：渐进式 Rehash 期间，查找一个 key 的流程是什么？

查找时先查旧 table（`ht[0]`），如果找到直接返回；如果没找到，再查新 table（`ht[1]`）。插入操作只插入新 table（同时触发一步 rehash）。删除和修改操作两个 table 都检查。这样保证 rehash 期间数据一致性，且每次操作的额外开销仅为 O(1) 的一步迁移。

## 追问 2：Redis 的 dict 如何解决 hash 冲突？

使用链地址法（Separate Chaining）。每个桶（bucket）是一个链表头，hash 值相同的 key 挂在同一个链表上。`dictEntry` 结构包含 `next` 指针指向下一个同桶 entry。查找时遍历链表逐个比较 key。当链表过长时（负载因子超过阈值），触发 rehash 扩容（size 翻倍到下一个 2 的幂）。

## 追问 3：为什么 Redis 用跳表而不是红黑树实现 Zset？

① 实现复杂度：跳表实现简单（几十行代码），红黑树复杂（旋转、变色逻辑多）；② 范围查询：跳表天然支持 O(log N + M) 范围查询（找到起点后沿最底层链表顺序遍历），红黑树需要中序遍历，实现更复杂；③ 并发友好：跳表局部修改不影响全局结构，红黑树旋转影响范围大；④ 内存局部性：跳表底层链表连续，缓存友好；⑤ 可调性：跳表通过调整层数概率（p=0.25 vs p=0.5）控制空间时间权衡，红黑树没有这种灵活性。
