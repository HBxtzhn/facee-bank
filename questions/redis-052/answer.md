1. **核心概念**：
   - **缓存击穿**：某个热点 key 过期瞬间，大量并发请求直接打到数据库
   - **缓存穿透**：查询的数据在缓存和数据库中都不存在，每次请求都穿透到数据库
   - **缓存雪崩**：大量 key 同时过期或 Redis 宕机，导致大量请求直接打到数据库
2. **关键细节拆解**：
   - **缓存击穿**：
     - **原因**：热点 key 设置了过期时间，过期瞬间并发请求全部 miss
     - **解决方案**：
       - **互斥锁（分布式锁）**：只允许一个线程查库并回填缓存，其他线程等待
       - **逻辑过期**：不设置物理 TTL，在 value 中记录逻辑过期时间，过期后异步更新
       - **永不过期 + 后台刷新**：key 不设过期时间，通过后台任务定期更新
   - **缓存穿透**：
     - **原因**：恶意请求或业务异常导致查询不存在的数据
     - **解决方案**：
       - **布隆过滤器**：在缓存前置布隆过滤器，拦截不存在的 key
       - **缓存空值**：查询数据库为空时，缓存一个空值（如 `""` 或特殊标识），设置较短 TTL
       - **参数校验**：在入口层校验参数合法性，拦截非法请求
   - **缓存雪崩**：
     - **原因**：大量 key 同时过期 / Redis 宕机 / 缓存服务不可用
     - **解决方案**：
       - **过期时间加随机值**：避免大量 key 同时过期
       - **多级缓存**：L1 本地缓存 + L2 Redis，降低 Redis 压力
       - **限流降级**：Sentinel/Hystrix 限流，服务降级返回兜底数据
       - **Redis 高可用**：哨兵/集群模式防止 Redis 宕机
       - **数据预热**：上线前预加载热点数据

## 扩展知识

- **布隆过滤器原理**：使用多个哈希函数将 key 映射到位数组中，查询时所有位都为 1 则"可能存在"，有 0 则"一定不存在"。有一定误判率但不会漏判，适合拦截大量不存在 key 的请求。
- **互斥锁 vs 逻辑过期**：互斥锁保证强一致但降低吞吐量（其他线程阻塞等待）；逻辑过期保证高可用但存在短暂数据不一致（旧数据继续提供服务直到异步更新完成）。
- **缓存雪崩的连锁反应**：大量请求打到数据库 → 数据库连接池耗尽 → 数据库响应变慢 → 更多请求超时 → 系统整体不可用。
- **实际应用**：三种问题可能同时出现，需要综合方案：布隆过滤器防穿透 + 分布式锁/逻辑过期防击穿 + 随机 TTL + 高可用架构防雪崩。

## 对比表格

| 问题 | 触发条件 | 影响范围 | 核心解决思路 | 代价 |
|------|---------|---------|-------------|------|
| 缓存击穿 | 单个热点 key 过期 | 单个 key 的并发请求 | 互斥锁 / 逻辑过期 | 吞吐量降低 / 短暂不一致 |
| 缓存穿透 | 查询不存在的数据 | 所有不存在 key 的请求 | 布隆过滤器 / 缓存空值 | 误判率 / 额外内存 |
| 缓存雪崩 | 大量 key 同时过期 / Redis 宕机 | 全局请求 | 随机 TTL / 高可用 / 限流 | 架构复杂度增加 |
