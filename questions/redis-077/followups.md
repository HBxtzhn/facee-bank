## 追问 1：Watch Dog 为什么每 10s 续期一次，而不是 30s 到期时再续？

① 预留缓冲时间：10s 续期一次，即使某次续期因网络抖动失败，还有 20s 的缓冲期可以重试，避免锁意外过期；② 避免临界点竞争：如果在过期瞬间续期，可能与其他线程的加锁请求产生竞争；③ 分散压力：多个客户端的续期请求分散在时间轴上，避免集中到过期时刻造成 Redis 瞬时压力。

## 追问 2：如果业务执行时间不确定，如何设置合理的 lockWatchdogTimeout？

建议：① 评估业务最大执行时间（P99 延迟），设置 `lockWatchdogTimeout` = 最大执行时间 * 2~3；② 默认 30s 适用于大多数场景（毫秒级操作）；③ 如果业务涉及外部调用（如 HTTP、数据库），考虑超时时间 + 重试次数，适当增大；④ 监控锁的续期日志，如果频繁续期说明 timeout 设置过小；⑤ 对于长时间任务，考虑分段加锁或使用其他方案（如状态机 + 任务队列）。

## 追问 3：Watch Dog 和 Redis 主从切换结合会有什么问题？

主从切换时，如果主节点在加锁后、Watch Dog 续期前宕机，锁数据可能未同步到从节点。新主节点没有锁信息，其他客户端可以获取锁，导致并发问题。Watch Dog 无法解决这个问题，因为它是客户端机制，不感知集群拓扑变化。解决方案：① 使用 RedLock（向 N 个独立节点加锁）；② 使用 ZooKeeper 等强一致中间件；③ 业务层做幂等检查和补偿。
